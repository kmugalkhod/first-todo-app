Draft product requirements · Shared MVP

Shared work without heavyweight project management.

The selected release supports small groups sharing projects, tasks and context. It deliberately stops before subscriptions, automation, calendar sync, AI and native applications.

Primary loop

Create project → invite → assign → discuss → complete.

Product boundary

2–20 person teams, responsive web only.

Trust boundary

Membership and roles checked on every server action.

Shared-work model

flowchart LR
  U[Authenticated user] --> P[Project]
  P --> M[Membership: Owner / Editor / Viewer]
  P --> S[Sections]
  S --> T[Tasks]
  T --> A[One assignee]
  T --> C[Comments]
  P --> E[Activity events]
  T --> ST[Sub-tasks]

Release requirements

AreaMust shipMust not expand into
IdentitySign in/out and internal user recordSSO, SCIM or enterprise controls
MembershipInvite, accept, remove; Owner/Editor/ViewerWorkspaces, billing and organisations
TasksProjects, sections, labels, priority, one assignee, date/time, sub-tasksDependencies, deadlines, duration and time tracking
CollaborationPlain-text comments and activity feedAttachments, notifications and rich mentions
ViewsInbox, Today, Upcoming, project list and searchCalendar sync, board view and automation

Release gates

  1. Owner creates a project and invites an Editor.
  2. Editor creates, assigns, comments on and completes a task.
  3. Viewer can read but cannot mutate data.
  4. Non-members cannot retrieve project data by search, URL or action.
  5. Today and Upcoming display only accessible, incomplete work.

Decisions still needed

  • Authentication and sign-in provider
  • Database, hosting and backup policy
  • Email invitation delivery and expiry policy
  • Whether Viewer role ships in v1 or immediately after Editor collaboration
  • Product name, domain, privacy and terms copy
